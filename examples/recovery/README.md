# recovery —— 恢复

崩在半路的现场 → 派生现场 → 显式续跑。

## 这个示例讲什么

进程会挂、会被 Ctrl-C、会被机器回收。MoS4J 的口径是**「日志即事实」**：
崩掉的那一轮在日志里就是缺尾巴，重开时框架认得出「这一轮没收尾」
「那次调用还悬空」，剩下的由宿主决定。

三条纪律：

- **派生是纯读**：`interruptedTurn()` / `hangingCalls()` / `pendingApprovals()`
  不写日志、不改状态、不推进序号——想知道现场就问，问多少次都一样。
- **不自动续跑**：框架不会自己拾起挂起的轮次（那等于替你决定「刚才那次副作用要不要重做」）。
  必须宿主显式 `resume(...)`。
- **续跑沿用原轮次号**：审批决定的复用键是 `(轮次, 调用 id)`，轮次号一变就匹配不上。

## 怎么跑

```bash
export OPENAI_API_KEY=sk-...
export OPENAI_MODEL=gpt-4o-mini

./mvnw -Pexamples -pl examples/recovery -am test

java -cp ... net.hegq.mos4j.examples.recovery.RecoveryExample
```

主程序会造一个「崩在半路」的现场（开了轮、批了准、声明了调用，
但没回填结果、没收尾），打印派生出来的现场，然后显式续跑。

## 看什么

- 现场：`被中断的轮次=1`，`悬空调用: c1 read {...}`。
- 续跑后：日志里多了一条**真实**的 `tool/result`（不是投影里那种合成失败回执），
  轮次号还是 1，那一轮以 `completed` 收尾。

## 边界

- 没有可续的调用时抛 `NothingToResumeException`，**那一轮保持挂起**
  （不写 `turn/end`：收尾等于把「还欠一次调用」的事实抹掉）。
- 续跑走的是**普通安全链**：守卫裁决、审批、审计照常；
  同一轮同一次调用已批过的，复用批准（复用也在审计里留痕）。
- 续跑不新开一轮，也不补 user 消息（那一轮的输入已经在日志里）。
